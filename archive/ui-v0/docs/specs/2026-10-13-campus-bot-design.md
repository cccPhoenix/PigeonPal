# 校园伙伴：第一版 UI 设计说明

日期：2026-10-13

## 定位与范围

一个固定身份的校园伙伴，兼具轻量个人助理能力。用户可以自然聊天、请求个人总结和文字润色，并接收来源通知与自己设置的提醒。

第一阶段交付可交互的本地网页原型，展示完整流程。聊天与写作回复采用明确标注的演示内容，通知使用演示数据；模型、真实网站采集、系统通知和后台调度在后续接入。复制、收藏、修改称呼与提醒管理可在原型中实际操作。

参考用户提供的 DS Bot 截图，以及下方固定版本的源码。布局、组件、样式和占位形象独立编写；不复制该项目的角色图形、SVG 路径或组件代码。第一版不引入多个 bot、群聊和插件管理。

## 页面布局

桌面采用左侧导航、右侧聊天的两栏布局。侧栏约 260 px，聊天正文居中，阅读区域约 820 px，输入框与正文区域对齐。较窄窗口收起侧栏，通过菜单打开；窄屏不得横向溢出。

侧栏顶部为产品名，接着是固定 bot 的头像和名字。默认名字为“小浙”，可以修改；它始终是同一个身份，不因频道改变。

侧栏分为以下入口：

- 和小浙聊天：闲聊、个人总结、文字润色、交代提醒。
- 校园通知：第一个来源频道，通知附带来源名称和原通知链接；后续可扩展更多来源频道。
- 收藏：保存的消息，保留所属频道，可返回原消息。
- 提醒：待处理和已完成的提醒，可新增、修改时间、完成或取消。
- 设置：固定在侧栏底部，编辑用户称呼、bot 名字、头像、主动消息开关和安静时段。

聊天顶部显示小头像与 bot 名字，点击打开资料面板。来源频道同时显示来源名称。不显示多个 agent 的任务进度或工具执行日志。

## 视觉与头像

整体采用近白背景、浅灰侧栏、浅灰 bot 气泡、深色用户气泡和少量蓝色点缀。使用系统中文字体，正文约 15 px、行高约 24 px，保留足够留白。

首版建议颜色：主背景 `#FAFAFA`，侧栏 `#F3F4F6`，bot 气泡 `#ECEEF1`，用户气泡 `#202327`，强调色 `#5277EA`。这些是本项目的初始选择，不复制参考项目的主题表。

头像从统一的 bot 资料读取。侧栏、顶部和消息列表共用同一张占位图，设置中替换一次即可同步变化。占位形象使用独立绘制的简洁图形；用户可以换成自己的图片。

消息头像约 36 px，位于 bot 气泡外侧、顶部对齐。同一个 bot 连续发送的一组消息只在第一条显示头像，后续气泡保留相同缩进。用户消息位于右侧，第一版无需用户头像。聊天记录内头像保持静止。

## 消息类型与操作

### 普通聊天

默认短气泡，允许连续两条回复。时间按消息组适度显示。用户分条输入不要求界面逐条生成回复。

每条消息都保留稳定标识、发送者、频道和时间。收藏、提醒、定位原文均引用消息标识，不能用正文内容代替标识。

通用操作位于气泡下方：复制、收藏、更多。鼠标悬停或键盘聚焦时显示；触屏提供可见的更多入口。菜单支持点击外部或按 Escape 关闭。

复制成功后显示“已复制”；失败时提供手动选择正文的方式。收藏图标表达已收藏状态，再次操作可取消。第一阶段的更多菜单提供引用回复；跨应用转发不设置成无法使用的按钮。

### 通知

通知由 bot 的简短语句、关键事实、来源与原通知入口组成。明确区分首次发现通知和已设定的到点提醒。

概括优先展示主题、时间、地点、截止时间与必要的参与条件；原文缺失的信息不补造。用户尚未表示参加时使用邀请语气，设定提醒后再使用“不要忘记”的提醒语气。

通知下方的“收藏”“提醒我”可持续显示。原型的虚构报告会必须标为“示例”，不得暗示为真实校园活动，也不得把来源主页冒充为该活动的原通知链接。演示原通知可在本地详情面板查看，后续替换为真实 URL。

频道有新消息时显示未读标记。用户正在阅读历史消息时，新消息不强制把页面滚到底部，提供“新消息”入口。用户位于底部时正常跟随消息。

### 个人总结与文字润色

用户在主聊天中提出请求、提供素材，bot 在聊天里返回正文。个人总结基于用户提供的经历，不能杜撰事实。

长正文支持展开和收起，操作包括“复制全文”“收藏”“继续修改”。收起只是展示方式，复制仍取得完整正文。选择继续修改时在输入框显示所针对的文本，用户可以修改要求或取消引用。

改写产生新消息，保留旧版本，避免覆盖用户之前看到的内容。只修改第二段等请求应保留被修改对象的上下文。

### 提醒

创建提醒后，用简短消息明确确认内容和具体日期、时间。存在歧义时需要澄清，不能默默猜测。

到点消息沿用同一个 bot 的头像和气泡，附“完成”“稍后提醒”。稍后提醒允许选择时间，不产生两个同时活跃的重复提醒。完成和取消操作同步更新提醒页。

原型可提供明确的“预览到点消息”入口，验证消息到达和处理流程。不能把页面内预览称作已完成后台持续提醒，也不能承诺电脑休眠时仍准点执行。

## 数据与设置

本地原型可保存收藏、提醒记录、用户称呼和 bot 资料。刷新后恢复；本地存储失败时明确反馈。原型不上传头像或聊天内容，也不配置外部账号。

所有频道共用同一份身份和用户偏好，频道保留各自的消息历史。通知数据与提醒记录分开管理：通知被收藏，不自动意味着用户参加活动或创建提醒。

主动消息开关和安静时段在界面中有清楚状态。真实调度接入后再确定到期提醒是否绕过安静时段；第一阶段仅展示并保存偏好，不宣称已执行系统级策略。

## 原型验收场景

1. 在主聊天输入消息，显示自己的气泡和带头像的演示 bot 回复。
2. 查看一个来源频道的通知，打开演示原文，收藏，再从收藏页返回消息。
3. 展开写作正文、复制全文、引用该正文继续修改，查看新版本。
4. 新增提醒、修改时间、预览到点消息，完成或稍后提醒，检查列表同步。
5. 修改称呼、bot 名字或头像，确认各处一致；刷新后恢复。
6. 用键盘打开和关闭消息菜单；缩窄窗口后仍能导航、阅读和发送。
7. 阅读历史时出现演示新消息，保持当前位置，通过新消息入口定位。

## 仓库参考与独立设计决策

参考版本：`84571450a3ce91413f8c7cf005c84a7bc7754efd`。以下结论来自源码静态阅读，没有安装或运行 DS Bot。

| 源码事实 | 对本项目的启发 |
|---|---|
| 客户端使用 React，并通过 DSH 的 slots 接入侧栏、顶部栏和消息节点 | 按界面职责拆分组件；原型独立运行，不依赖 DSH 插件体系 |
| `lookOf` 统一解析头像外观；`BotMark` 支持自定义图片和内置 SVG 角色 | 用统一 bot 资料和头像组件，角色图片独立制作 |
| `AssistantCell` 的普通单聊回复调用 `Bubbles` 时没有传入头像；群消息会传入 `lead` | 单聊消息头像需要在自己的消息布局中明确实现；采用组内首条、顶部对齐 |
| `Bubbles` 将正文和 `MessageTools` 分离；当前工具栏提供表情回应、引用回复和更多，更多内包含复制、下载 | 正文渲染与消息操作分开设计；本项目加入收藏、通知提醒和写作操作 |
| `themes.js` 集中管理界面颜色，`styles.js` 根据变量生成样式 | 将颜色和间距集中配置，不搬运原项目 CSS |
| 聊天记录头像可保持静止，侧栏和顶部头像可以根据状态变化 | 先保证阅读稳定，第一版不要求复杂角色动画 |
| `host/schedules.js` 接入 DSH 的 schedule 服务；调度服务可缺失 | 后续需要真正的调度层，不能把 UI 定时预览当成持续运行能力 |

## 后续需要确定的产品行为

真实来源接入前，需要确定哪些通知主动推送，以及普通内容是否汇总。后台提醒接入前，需要确定运行方式、安静时段与到期提醒的优先关系。这些决定不阻碍当前 UI 原型，但不能在第一阶段暗中当作已经确认的需求。
